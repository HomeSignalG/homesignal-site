# Denton County permit identity: stop merging unrelated features that reuse a PermitID (DESIGN ONLY, 2026-10-14)

**Status: design. Nothing here is applied, deployed or written to production.** No SQL in this file is to be run; the
statements are described, not supplied. Owner of the decision: founder (cross-repo and migration-shaped).

## 1. The defect, with the numbers measured

Registry `denton-county-dev-permits` (`gis.dentoncounty.gov/.../DEV_Permits/FeatureServer/0`), `column_map.case_number = PermitID`.

| measure | value | where measured |
|---|---:|---|
| features in the layer | 56,500 | `denton-launch-investigate.py` section 1 (all features paged, identity = `OBJECTID`) |
| distinct `PermitID` | 56,305 | same |
| `PermitID` values carried by more than one feature | 149 | same |
| of those, features more than 30 m apart | 119 | same |
| `OBJECTID` unique | yes | same |

Everything downstream keys on `source_key = arcgis:<registry_id>:<PermitID>`
(`sources/arcgis.ts`, `source_id: arcgis:${registry_id}:${identityFromFields(...) ?? caseNo ?? rowId(row) ?? title}`).
Two unrelated official features with one `PermitID` therefore become ONE project:

* `geo.n5_geom` is keyed `(source_key, feature_id)` (feature_id is the OBJECTID), so both geometries are stored under one key.
  The publish step then does `ST_Union` of every feature of the key before clipping (`docs/n5-generation-publish.sql`, membership
  and marker steps). A point pair 5 km apart becomes a multipoint; the ZIP membership list is the union of both places, and the
  representative point rule (`POINT_MIN_XY` for dimension 0) picks whichever is westmost, which may be the other permit's location.
* `public.app_projects` is unique on `(zip, source_key, source_seq)` and `source_seq` is a per-ZIP ordinal
  (`docs/n5-unit-a-shadow.sql` header: "not a stable identity"), so descriptive fields are borrowed from one deterministic row.
  The second permit's name/status/date can be shown on the first permit's dot.
* The audit reports these as `ambiguous_identity` / `eligibility.ambiguous_ids` (UNKNOWN), correctly refusing to compare a dot
  with "the" publisher point when the publisher has two.

## 2. Design goal

A reused `PermitID` must produce DISTINCT source keys for features that are different records, without changing the key of any
record whose key is already stored, linked, posted or in the longitudinal history (CLAUDE.md "Permanent historical intelligence":
current product state may change, historical evidence must survive; identity changes must be auditable and reversible).

## 3. Smallest correction (recommended)

**Keep the legacy key for exactly one feature per reused id; give every other feature of that id an alias key that contains its OBJECTID.**

```
legacy key (unchanged, history preserved)   arcgis:denton-county-dev-permits:<PermitID>
alias key (new, only for the 2nd..nth)      arcgis:denton-county-dev-permits:<PermitID>#<OBJECTID>
```

* The "primary" feature of a reused id is the one with the LOWEST `OBJECTID`. This is a pure function of the publisher's data, so
  every ZIP, run and generation derives the same answer, and it matches the oldest record, the one most likely to carry history.
* Ids that appear once (56,156 of 56,305) are untouched: their keys, `source_seq`, posts, memberships and history do not move.
* Why not `identity_fields: ["PermitID","OBJECTID"]` (the Brunswick/NYC precedent, `source-key-quality-repair.md`)? That option is
  all-or-nothing per registry: it would rekey all 56,500 records and orphan every stored key, post and capture. It is the right tool
  when the whole column is not an identifier; here only 149 ids are affected.
* Why not derive "is this id reused?" at fetch time? The engine reads a 3-mile envelope per ZIP, so one of the two features may be
  outside the radius; the same feature would get different keys on different pages. The reused set must be global.

### 3.1 Where the reused set comes from (computed, never typed; claims rules 7 and 8)

A new data file `supabase/functions/get-address-report/identity-aliases/denton-county-dev-permits.json`, GENERATED by a read-only
script (extends `denton-launch-investigate.py` section 1) from a full paged scan of the layer:
`{ "<OBJECTID>": "<PermitID>#<OBJECTID>" }` for every non-primary feature. It carries the scan date, feature count, distinct-id count
and an order-independent fingerprint (`sum` of per-row md5 prefixes, so no collation question arises) that a CI check recomputes from the
live layer daily. A new reuse appearing at the publisher turns that check red; the file is then regenerated by the same script.
The layer is small enough (56,500 rows, about 30 requests) for the daily check to be cheap.

## 6. Risks

1. **A key that already has history changes meaning.** The primary keeps the legacy key, but until now that key stood for BOTH features. Anything
   recorded against it (a MAPS draft, a capture key `v1|zip|project|...`, a `social_posts` row) may describe the second feature's data.
   Mitigation: list every stored reference to the 149 keys before step 3 and decide per reference; do not rewrite approved or published posts.
2. **"Lowest OBJECTID is the primary" can be wrong** if the publisher renumbers OBJECTIDs (a full republish/truncate-and-load does this on
   FeatureServers). Then primary and alias swap and the legacy key jumps to the other permit. Mitigation: the daily fingerprint check goes red on any
   change to the (id -> OBJECTID set) mapping, and a regeneration is a reviewed change, never automatic. The same risk already exists for every
   layer whose identity falls back to `rowId`.
3. **OBJECTID is not a business identifier.** The alias is a disambiguator for one layer, not a permit number; it must never be displayed as one.
4. **n5_shard change (touch point 3) is the riskiest edit**: it is the only consumer that cannot handle a composite identity today
   ("compound identity ... is not supported by this pass"). A mistake there silently reclassifies projects as `legacy_unsupported`.
   Needs a fixture with a real duplicate pair and the generation proof (`n5_generation_pg`).
5. **Dedup key**: `dedupeExactPermits` includes `source_id` in its identity, so two features that are byte-identical at the publisher but now carry
   different aliases would stop collapsing. Of the 149 groups, those that are true publisher duplicates (same attributes, same point) should
   NOT be aliased. The generating script must classify each group (same location within 30 m and same attributes = duplicate, keep one key;
   otherwise = distinct records, alias) and report both counts. Measured so far: 119 of 149 groups are more than 30 m apart; the other 30 are
   not yet classified.
6. **Cross-repo**: the longitudinal tables and `n5_shard` live partly in homesignal-ingest/homesignal-site; the change set is site-side but the
   daily build is shared. Coordinate with the N5 owner before step 3 (concurrent-session rule).
7. **Other layers have the same shape** (Brunswick, desoto, cabarrus, ... in `source-key-quality-repair.md`). This design is deliberately
   per-registry and data-driven so it can be reused, but it is NOT a claim that Denton is the only affected registry.
8. **Cost of doing nothing**: 119 reused ids with features more than 30 m apart can draw a dot at the wrong one of two real places. The audit
   already withholds PASS for any ZIP showing such an id (UNKNOWN), so the launch risk is a delayed PASS, not a wrong claim.

## 7. What was NOT done

No registry change, no engine change, no alias file, no SQL, no deploy. This document is the whole deliverable.
