- The script's `h1` field for the *initial* response reads

- `localNews: 0` came from a selector (`[data-tile="news"] .card, .newsCard`) that was never

- Byte counts differ between instruments (14,629 via `pg_net` `length()` = characters;

## 6 · Robots / indexability trace

`app_refresh_zip` (materializer) → `app_community_meta.indexable` → three consumers.

**The exact formula, verbatim from `pg_get_functiondef(app_refresh_zip)`:**

```sql
((_nd+_nf+_nc)>0 and (_ndp > 0 or _nfc >= 3)),
```

`_nd` development records · `_ndp` development projects · `_nf`/`_nfc` facilities ·
`_nc` app_changes placements for the ZIP (**Alerts**) · `_nm` forward meetings.

1. **What does the server initially emit?** `noindex, nofollow`, unconditionally, for every
   ZIP. No `X-Robots-Tag`.
2. **Can JavaScript change it?** Yes — `setIndexable()` rewrites the `content` attribute of
   `#robots-meta`.
3. **Does it currently?** Yes, at `community.html:53`, after **three awaited Supabase reads**
   (`coverageStatus`, `community`, `coverageState`) plus the `partials/shell.html` fetch.
4. **Which field controls it?** `app_community_meta.indexable`, AND `data_quality='pass'`.
5. **Exact current formula:** the SQL above.
6. **Does Alerts substance participate?** **No.** `_nc` appears only in the trivial
   `(_nd+_nf+_nc)>0` guard; the deciding clause is `(_ndp > 0 or _nfc >= 3)` — development
   projects and EPA facilities. `_nm` (forward meetings) is computed and **never used**.
7. **Controls A–F:** every one is served `noindex` initially. Post-JS, A/C/E/F flip to
   `index, follow` (all `indexable=true`+`pass`); B and D stay `noindex`. **Control C flips
   to `index` with zero Alerts items** — the defect, reproduced end to end.

`homesignalmap.html` uses the **same flag and the same JS-flip pattern**
(`homesignalmap.html:11` default `noindex`; `setIndexable` at :530 from the same
`app_community_meta.indexable`). `scripts/gen_sitemap.py` reads the same flag and emits
**both** URL types from it.

## 7 · Alerts content delivery trace

| tile | data source | in initial HTML | embedded as JSON | needs another request | DOM created by |
|---|---|---|---|---|---|
| Local News | `app_changes` where `category='Local News'` (`lib/data.js::news`) | **no** | no | yes | **nothing on `community.html`** |
| Government Notices | `app_changes` non-`Local News`, minus `Public meeting%` (`lib/data.js::changes`) | **no** | no | yes | inline `page.innerHTML`, `HS.tpl.miniCard` |
| Upcoming Meetings | live `meetings` on the ancestor chain, `meeting_date >= now()` (`lib/data.js::meetings`) | **no** | no | yes | inline `page.innerHTML` summary card |

> **Could a non-JavaScript HTML consumer read the Alerts content?**
> # NO.
> Not one item's text, title or link exists anywhere in the initial response.

**The render waterfall is deep and strictly sequential:** `fetch(partials/shell.html)` →
`coverageStatus` → `community` → `coverageState` → `projects` → `facilities` → `changes` →
`meetings` (which itself walks up to 6 sequential `communities` queries before its own
`meetings` query). Eight-plus round trips before any Alerts text exists.

### 🔴 `community.html` does not render Local News at all

`community.html` calls `projects`, `facilities`, `changes` and `meetings`. It **never calls
`HS.data.news()`**. The only caller is `alerts.html:72` — and `alerts.html` is
`noindex, nofollow`, `Disallow`ed in `robots.txt`, and appears **0 times** in `sitemap.xml`.

Consequences, measured against the readiness matrix:

- **575 ZIP pages pass Rule F only via Local News** (`lnj+gn+um >= 3` but `gn+um < 3`).
  Gating on Rule F as written would index those pages for content the page does not show.
- **6,496 pages pass on community-visible substance alone** (`gn+um >= 3`).

The indexed page also renders only a **slice** of what it fetches: `notices.slice(0,2)` and
a single meetings card naming `meetings.slice(0,2)`. So even the tiles it does render are
summarised, not listed.

## 10 · Recommended gate architecture — **Option 1, applied per page type**

**Not implemented. Design only.**

One flag, `app_community_meta.indexable`, currently gates **two different page types** that
show **different content**:

| page | shows | correct substance test |
|---|---|---|
| `homesignalmap.html?zip=` | development records + EPA facilities | the **existing** `(_ndp > 0 or _nfc >= 3)` |
| `community.html?zip=` | Government Notices + Upcoming Meetings (+ dev/facility summary) | **Rule F** |

The measurement settles which of the four options is right, and it rules out three of them:

- **Option 1 (Rule F replaces the gate) — CHOSEN, scoped per page type.** Rule F becomes the
  gate for `community.html`; the existing development/facility test is **kept unchanged** for
  `homesignalmap.html`. Two flags, one per page type.
- **Option 2 (OR) — rejected.** A page indexable if *either* test passes leaves
  `community.html` indexed for all 5,153 pages that have development substance and thin
  Alerts. That is precisely today's defect, preserved.
- **Option 3 (AND) — rejected.** It would un-index legitimate development-only pages *and*
  legitimate Alerts-only pages. Strictly worse for both products.
- **Option 4 (unified score) — rejected.** Collapsing two products into one number is the
  same category error as today's single flag, just with more arithmetic.

**The receipt that decides it:** of the 5,153 pages indexed today that fail Rule F,
**5,153 (100%) carry valid development or facility substance; zero are indexed on nothing.**
The existing gate is not broken — it is being asked to answer a question it was never
written for.

### The change surface

`public.app_refresh_zip` already computes everything needed. Add one column and one
expression; change no other file's logic:

```
_nc  -> already the ZIP's app_changes count      (needs splitting: non-weather Alerts only)
_nm  -> already the forward-meetings count       (currently computed and UNUSED)
```

- `app_community_meta.indexable` — **unchanged semantics**, keeps gating `homesignalmap.html`.
- `app_community_meta.indexable_alerts` — **new**, `data_quality='pass' AND rule_f`.
- `community.html:53` reads `indexable_alerts` instead of `indexable`.
- `scripts/gen_sitemap.py` emits the `community.html?zip=` URL from `indexable_alerts` and
  the `homesignalmap.html?zip=` URL from `indexable` — today one flag emits both.

Automatic recalculation is preserved: `app_refresh_zip` runs per ZIP on the existing
materializer cadence with `on conflict … do update`, and `sitemap.yml` republishes daily.

### ⚠️ The Rule F variant question the founder must settle

Rule F counts Local News, which `community.html` does not render. Two honest resolutions —
**do not ship the gate without picking one**:

| | gate | pages | note |
|---|---|---:|---|
| **F-visible** | `gn + um >= 3` | **6,496** | index only for content the page actually shows. Ship-ready today. |
| **F-full** | `ln_journalism + gn + um >= 3` | **7,071** | honest **only if** Local News is added to `community.html` first (+575 pages) |

Indexing a page for content it does not display is the thin-content failure this whole
programme exists to avoid. **F-visible is the safe default**; F-full is correct the moment
Local News renders.

## 11 · Server-rendering design (not implemented)

The initial HTML carries no Alerts content, so progressive enhancement requires real HTML
first. **There is a hard architectural constraint that must be surfaced, not designed
around:**

> ⛔ `?zip=` is a **query parameter on one static file**. GitHub Pages cannot vary a response
> by query string. Server-rendering therefore requires **per-ZIP paths** — and site
> `CLAUDE.md` §0 states *"No per-community HTML files"*, with `404.html:9` repeating *"No
> per-ZIP files … the canonical URL is `homesignalmap.html?zip=`."*

**This conflicts with a prime directive and needs founder ratification.** The reconciling
argument, offered but not assumed: §0's intent is that *adding a community must require zero
engineering*. A **generated** artifact emitted by CI from the materialized read model
satisfies that intent exactly as `sitemap.xml` already does — 23,381 URLs, regenerated daily
from `app_community_meta` and committed by `sitemap.yml`, with no per-community engineering.
Hand-authored per-community files are what §0 forbids; generated ones are the existing pattern.

| | design |
|---|---|
| **Code surfaces** | new `scripts/gen_zip_pages.py` (mirrors `gen_sitemap.py`); new workflow or a step inside `sitemap.yml`; `community.html` kept as the JS app shell |
| **Data contract** | read **only** `app_community_meta` + the same `app_changes` / `meetings` queries `lib/data.js` already issues. **No second data path** — one read model, two renderers |
| **Rendering point** | CI, on the existing daily cadence, committed to `main` like `sitemap.xml` |
| **Government Notices** | server-render the same rows `changes()` returns, same category filter, same `Public meeting%` exclusion |
| **Upcoming Meetings** | server-render the same forward-dated, chain-scoped, 12-capped list |
| **Local News** | server-render **only if** the founder adopts F-full; otherwise omit (the page does not show it today) |
| **Empty-tile behavior** | render the existing honest-empty copy verbatim — never omit the section, never imply content exists |
| **Escaping / security** | reuse `lib/templates.js::esc` semantics. Publisher titles and government notice text are **untrusted input**; every interpolation escaped, `record_url` attribute-escaped |
| **Failure behavior** | fail closed — a ZIP whose generation errors keeps its current shell and `noindex`. Never emit a half-rendered page as indexable |
| **Cache implications** | static files on Pages CDN; freshness bounded by the daily job, which is why the rendered HTML must carry the same "last verified" copy the JS path shows |
| **JS after SSR** | **yes, retained.** JS rehydrates and takes over interactivity (follow, subscribe, share). SSR supplies the crawlable floor; JS supplies the app |

Two page-quality items the design should not silently inherit: `community.html` renders only
`notices.slice(0,2)` and a single meetings summary card, and **no page ever sets a per-ZIP
`<title>` or a `<link rel="canonical">`**. Both are cheap to fix at the same surface and both
matter more for SEO than structured data.

## 14 · Decision

# A — CRAWLER BLOCKER CONFIRMED; IMPLEMENTATION UNIT READY

Production measurement confirms both halves of the prior diagnosis and adds a third defect
the prior unit did not have:

1. **Initial HTML carries no Alerts content** — 22 characters of visible text, empty
   template, no ZIP identity, byte-identical for every ZIP.
2. **Indexability is decided by the wrong substance** — the gate's deciding clause has no
   Alerts term, and 5,153 pages are indexed with fewer than 3 Alerts items.
3. **New: `community.html` never renders Local News**, so 575 pages would be gated on
   content the page does not display.

The bounded implementation is now specifiable, and is specified in §10–§13.

**What this unit did NOT establish, stated plainly:** whether Google *actually* indexes these
pages today. The robots flip demonstrably works in a real browser, so the pages are
