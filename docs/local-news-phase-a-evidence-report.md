## Evidence 1 — Deterministic replay

- **Over-cap determinism (the Addendum's exact case):** ZIP **02108** has 77
  qualifying development rows for 48 slots (`development=48/77` in the refresh
  log — the same 48-of-77 the Phase A Addendum flagged as nondeterministic).
  After M1, repeated refreshes select the **identical** row set:
  development-selection digest `8e0c49ee5e0f1b0ba17bb613ff90227d` (48 rows) and
  page digest `7528b006392634c70dd20f72bb7979f7` on both runs.
- **Branch replay from source tables:** the pilot's Local News page section was
  reconstructed standalone from `alerts` (root-community, 14-day window,
  `created_at desc, id` top-48, source_ref-deduped) and compared to the stored
  `app_changes` rows: stored 48, expected 48, **0 rows differ in either
  direction**. Deterministic replay baseline established.

## Evidence 3 — Semantic equivalence of the ZIP lookup change

Before M2 was applied, both predicates were evaluated side-by-side for **every
candidate ZIP in the refresh universe** (the same union `app_refresh_batch`

> total_zips = **12,722**, mismatches (`old_id is distinct from new_id`) = **0**

equivalence is proven" — satisfied before apply, and the M2 migration would
have been a no-op refusal otherwise.)
