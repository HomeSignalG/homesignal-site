# JODY — National Development Map Indexing Root-Cause Audit (Google + Bing)

Audit only. Nothing was changed, deployed or submitted. Run 2026-11-11 ~16:00 UTC against live jodytracks.com, the
homesignal-site repo at `77d1ca1`, read-only Supabase queries and the Supabase API logs (last 24 h).

## A. Executive diagnosis

**The map pages are reachable, return 200, say `index, follow`, are self-canonical, are in the sitemap, and their data
APIs answer crawlers successfully. Nothing technical blocks indexing.** The problem is what a crawler finds when it
gets there, plus how little reason it has to come back.

Confirmed:
1. **The first HTML of every map page holds 6 words outside a `<template>`.** All visible content, H1 included,
   sits inside an inert `<template>` that JavaScript copies into the page. Without rendering, the page is a title and
   nothing else.
2. **After rendering, map pages are 95–97% identical to each other.** The template text (filters, legend, help)
   is the same on every ZIP. Only the place name, ZIP and up to 12 rows per list change.
3. **The rendered lists link nowhere indexable.** Rows go to `homesignalmap.html?addr=…` (noindex by design) or to
   outside agency sites. Maps are dead ends for crawling.
4. **Map pages get almost no internal links.** Only the sitemap and one link from each `/community/<zip>/` page.
5. **The map sitemap never signals a change.** 12,725 of 12,742 `<lastmod>` values are frozen at
   `2026-10-27T18:43:05Z`, because the change detector ignores `<template>`, which is where all map content is.
6. **Automatic Googlebot rendering of map pages is close to zero, and the renders it does do follow manual
   inspection.** Last 24 h of Supabase logs: Google-InspectionTool rendered ~15 map pages 20:53–21:00Z Nov 10;
   Googlebot rendered ~9 more 20:58–21:09Z the same evening; no other Googlebot map renders. Every call returned 200
   (avg ~80 ms, max 341 ms).

Supported hypotheses (not proven):
- Google is choosing not to crawl or index the maps because they look like 12,742 near-duplicate templated shells.
  The same development records also appear, as plain HTML, on the `/community/<zip>/` and
  `/community/<zip>/projects/` pages. That fits the reported "Discovered – not indexed" pattern.
- The young domain (Change of Address to jodytracks.com on 2026-10-15) and ~49,000 URLs published at once
  keep Google's crawl budget for the site low.

Unknown: Search Console per-URL status, Google-selected canonicals, crawl stats; Bing's per-URL crawl/index state.

## C. Ranked findings

**F1 — Map content exists only after JavaScript runs.** Confidence: high (measured).
- Evidence: `https://jodytracks.com/map/98402/` is 14,255 bytes. Outside `<template>` the visible text is
  "Development around Tacoma (98402) — Jody" (6 words); the 310 words inside `<template>` include the H1 and the
  only crawlable link (`/community/98402/`).
- Source: `homesignalmap.html` (the whole page is in `<template>`); `scripts/gen_zip_pages.py::MapTemplate.render`
  puts the ZIP H1, description and record count into that template.
- Affects: all 12,742 map pages.
- Fix: render a small, real static block **outside** the template in each map document. It should hold the H1, the
  record count, the top N records (name, type, stage, date, link to their project/community page) and links to
  `/community/<zip>/` and `/community/<zip>/projects/`. Use data already in the build (the Rule D plane / project
  pages data), not new copy. Leave the runtime alone.
- Why it helps: the first crawl pass sees real, ZIP-specific content without waiting for Google's render queue,
  which is what low-priority URLs on a new site wait longest for.

**F2 — Maps are near-duplicates of each other, and their facts duplicate the community page.** Confidence: high
(similarity measured); medium on the effect on Google.
- Evidence: template text similarity to 98402 is 0.974 for 01001, 33133 and 72712, and 0.954 for 59044. The
  `/community/98402/` page already lists the same development records in static HTML (370 words);
  `/community/98402/projects/` lists 6 projects.
- Fix: F1 makes each map's static part ZIP-specific. Separately, decide what the map page is FOR in search:
  - If it adds nothing a crawler can read beyond the community page, the honest options are
    (a) keep it indexable with F1's ZIP-specific summary, or
    (b) a founder call on consolidation.
  - Do not noindex or canonicalise without that decision. The index-all ruling (2026-10-26) stands until the
    founder changes it.

**F3 — Map pages are crawl dead ends.** Confidence: high.
- Evidence: rendered list rows link to `homesignalmap.html?addr=…` (`homesignalmap.html` `propertyHref`, line ~4881),
  which the page sets to noindex, or to outside agency records. No link from a map page reaches a
  `/project/…`, `/development/…` or `/community/<zip>/projects/` page.
- Fix: in F1's static block (and in the rails), link each record to its own indexable page where one exists
  (`/project/<…>/`, dossier).

**F4 — Few links point at map pages.** Confidence: high.
- Evidence: `gen_zip_pages.py` lines 940 and 1391 are the only generators of `/map/<zip>/` links (community nav,
  city page). Project and project-list pages do not link to their ZIP map (`/community/98402/projects/`: 0 map links).
- Fix: link `/map/<zip>/` from project-list and project pages, and from neighbouring ZIP sections.

**F5 — `map.xml` `<lastmod>` is frozen.** Confidence: high.
- Evidence: 12,725 of 12,742 map entries read `2026-10-27T18:43:05Z`. `scripts/page_semantics.py::projection`
  strips `<template>` before fingerprinting, so a map page's fingerprint never moves when its records change, so
  neither `lastmod` nor IndexNow ever fires for maps again.
- Fix: comes with F1. Once real content is outside the template, its changes move the fingerprint. Expect one
  mass-change IndexNow hold on the first deploy (the existing `allow_mass_change` resubmit handles it).

**F6 — The runtime replaces the static H1 with a weaker one.** Confidence: high, low impact.
- Evidence: rendered H1 reads "ZIP 98402" while the static one reads "Development around Tacoma (98402)".
- Fix: keep the place name in the runtime heading.

Checked and **not** a defect: HTTP 200 on sampled maps; `index, follow` static and at run time
(`setIndexable` keeps `/map/<zip>/` indexable); self canonical; `<base href="/">` resolves assets correctly;
robots.txt allows `/map/` and `/homesignalmap.html`; one host (non-www) across sitemaps and canonicals; data
APIs answer Googlebot and bingbot with 200.

## D. Google vs Bing

- **Shared:** F1–F6 apply to both.
- **Google:** logs show renders mainly right after URL Inspection, which matches "indexed after a manual request".
  Sequence is not proof of cause (Inspection fetches and live tests also render).
- **Bing:** the sitemap is read (map.xml: success, 12.7K discovered, last read Nov 5). bingbot rendered about 1 map
  in 24 h. IndexNow submitted all maps once: run `40563654708` on 2026-10-27 sent 25,450 URLs, HTTP 200 on all 3
  batches. That is why the "Not yet crawled" export lists no maps: they were not in it, not unsent. After that,
  F5 means maps were never sent again.
- The two `sitemap.xml` entries (www and non-www) in Bing: www could not be fetched from this sandbox (proxy 403).
  Check that `https://www.jodytracks.com/sitemap.xml` 301s to the non-www file.

## F. Minimal pilot

- **Change:** F1 + F3 + F6 for maps, F4 links on project-list pages. Shared code only (`gen_zip_pages.py`,
  `homesignalmap.html`), all ZIPs built the same way.
- **Pilot split:** a fixed, random half of ZIPs (by ZIP hash) gets the static block; the other half is untouched as
  the control. No manual inspection requests for either half.
- **Acceptance tests:**
  - built artifact: each pilot map has ≥ 1 ZIP-specific sentence and its records outside `<template>`;
  - no fabricated values (every listed record traces to a page record);
  - pilot-vs-pilot static similarity under 0.6;
  - fingerprint moves when records change (`test/indexnow-delta.test.mjs`);
  - existing `audit_index_all.py` gate still green.
- **Monitor 4–6 weeks:** count of pilot vs control maps indexed (Search Console export); Googlebot map renders per
  day from the Supabase logs; Bing indexed counts.
- **Rollout condition:** pilot indexed share clearly above control with no rise in errors. No promise of a number
  or a timeline.

## H. Not justified by this audit

- New sitemaps, a 50-state sitemap project, or more sitemap families.
- Mass IndexNow or manual URL submissions.
- noindex, canonical or redirect changes to maps (index-all ruling; needs founder decision and Search Console
  canonical evidence first).
- Fixing robots, status codes, host or API performance: all checked and fine.
- Geographic filler text.
