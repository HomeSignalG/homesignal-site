## Shard 662 halted three times, and the fix is a driver change

The freeze — the statement that copies a shard's slice of `preservation.app_project_identity`
into `geo.n5_frozen` — has always been ONE statement per prefix. That fit 540 shards. It does
not fit 662.

**Every halt was clean.** `geo.n5_frozen where z3='662'` was 0 after each one, so the insert
rolled back whole; the shard was never in a half-built state, it just never finished.

What was tried, in order, and what each measurement actually said:

1. **Re-run.** The first halt came while a 150-ZIP verification query of my own was running, so
   contention was a live hypothesis. It halted again with nothing of mine running.
2. **Index on `zip`, partial to the four remaining prefixes** (~4 MB). The freeze had been a
   `Parallel Seq Scan` over 3,172,292 rows / 1,125 MB — there is no index on `zip` at all, only
   the `(snapshot_id, app_project_id)` primary key. Cost 181,525 → 51,129. **Still halted.**
3. **Index keyed on the expression instead** (`left(zip,3)`), so the prefix became an Index Cond
   rather than a recheck. Cost → 38,407. **Still halted**, at ~120 s, while `app_refresh_sweep`
   and `dev_refresh_tick` ran alongside.

That third failure is the informative one: **the remaining cost is per-ROW, not the scan.** The
freeze does ~148k primary-key lookups into `public.app_projects` (4,382 MB) and writes ~148k
rows; no index on the read side can remove that, so the statement had to be split.

4. **ZIP4 buckets** — ten statements, `left(zip,4)`. It committed 6620 (42,302 rows, ~55 s) and
   lost 6621 (65,029) to the 110 s bucket timeout. Not fine enough, and the reason is structural:
   prefix 662 has only **four** non-empty ZIP4 buckets (6620 42,302 · 6621 65,029 · 6622 40,719 ·
   6625 398), so the largest is still 44% of the shard.
5. **Per ZIP** — 25 statements, `i.zip = <zip>`, cost **230** each. Freeze completed in ~5 minutes
   at a steady ~8,000 rows per statement, **148,448 rows across all 25 ZIPs**, and the shard ran
   through boundaries, association and verification to DONE.

Three things in that final form are load-bearing and easy to "simplify" back into a defect:

- **The predicate keeps `left(zip,3)` next to the ZIP equality.** It reads as redundant. The
  planner cannot prove a bare ZIP equality implies the partial index's prefix list, and without
  it EXPLAIN returns to the sequential scan — measured, not assumed.
- **The buckets are equalities, never a range.** A range needs an order; this database collates
  `en_US.UTF-8` while the bounds would be chosen by codepoint. That is CLAUDE.md rule 9, and the
  range form had already produced a real instance of it: its last upper bound was the prefix's
  arithmetic successor, which for prefix `999` is `'1000'`, and `'99900' > '1000'` as text — the
  final chunk would have selected **nothing**, silently. Caught by a test written while the range
  form was still on disk.
- **The ZIP list is read from `preservation.app_project_identity` itself**, not from the canonical
  ZIP registry. A ZIP present in the basis and absent from the registry would otherwise be skipped
  and the freeze would look clean.

The delete still runs once, before any ZIP, so a failed ZIP leaves a PARTIAL slice — and the
manifest gate immediately after compares projects, pairs and the order-independent checksum, so a
partial slice halts as `FREEZE_DRIFT` instead of being built on. Six offline assertions in
`scripts/test_recovery_batching.py` pin all of it against the shipped source.
