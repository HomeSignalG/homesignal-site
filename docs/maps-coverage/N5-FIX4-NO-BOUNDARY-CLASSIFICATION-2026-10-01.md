# Fix 4: the 706 canonical ZIPs with no boundary (2026-10-01)

**Question.** 706 of the 12,722 canonical ZIP pages have no Census ZCTA boundary, so Map 1 serves
them as `not_measured`. Is each one a legitimate non-ZCTA ZIP (PO Box, unique, decommissioned, or a
ZIP Census did not delineate), or a boundary HomeSignal failed to acquire or publish?

**Answer.**
- **0 are HomeSignal boundary omissions.** There is no TIGER/ZCTA acquisition or generation defect to
  correct.
- **704 are legitimate non-ZCTA ZIPs**, and **2 (84684, 84685) are ZIPs whose existence is not
  established**: no ZIP dataset and no Census delineation lists them.
- **All 706 stay `not_measured`**, as they are today.
- **No HomeSignal data changed.** Census was read through the database's request queue (pg_net):
  11 GET requests to `tigerweb.geo.census.gov`, all HTTP 200 (§7). No HomeSignal table was written.

*This receipt replaces the version committed in `46b1f6e`. An audit of that version found 26
problems. The main ones: a false "open item" about Fix 3 (retracted in §5), class names that
credited USPS with a third-party list, a hand-typed evidence file with wrong layer labels, and
"all 706 legitimate". Each is corrected below.*

## 1. The classification

Decided once, by `scripts/fix4_classify_no_boundary_zips.py`, from four inputs:
- the production export (`no-boundary-zips-2026-10-01.psv`);
- the Census evidence (`census-zcta-evidence-2026-10-01.json`);
- the Census code sets (`census-zcta-codes-2026-10-01.json`);
- the pinned **zipcodes 3.0.0** package (PyPI, released 2026-06-14).

The first three are generated by the database (§4). The output is
`docs/maps-coverage/fix4/no-boundary-zip-classification.csv`, one row per ZIP, and its
`.summary.json`. All are in `docs/maps-coverage/fix4/`.

**Where the type and "decommissioned" labels come from.** zipcodes 3.0.0's own METADATA says its
base data (ZIP type, and the decommissioned flag) is unitedstateszipcodes.org's CSV, "refreshed
manually on occasion" (refresh date unknown). USPS ZIP Locale Detail is used only to add active ZIPs
that base CSV lacks. So **none of these labels is a USPS statement**, and the class names say
"dataset", not "USPS". Most HomeSignal community builds, from Michigan onward, also took their ZIPs
from zipcodes 3.0.0. Utah and Colorado were hand-derived, and the 42-state build took counties from a
Census file.

| class | ZIPs | group | disposition |

| `PO_BOX_ZIP` | 498 | legitimate non-ZCTA | stays `not_measured` |
| `UNIQUE_ZIP` (one organization or building) | 107 | legitimate non-ZCTA | stays `not_measured` |
| `STANDARD_ZIP_NO_CENSUS_ZCTA` | 52 | legitimate non-ZCTA | stays `not_measured` |

| `HOMESIGNAL_OMISSION` | **0** | HomeSignal omission | would be corrected |

**Rules, in order:**
1. Census's current (2020) code set contains the ZIP → omission.
2. Otherwise, absent from the dataset → `NOT_IN_ZIP_DATASET`.
3. Otherwise, flagged inactive → `DECOMMISSIONED_IN_DATASET`.
4. Otherwise, the dataset's type.

**An omission is decided only by Census membership, never by ZIP type.** Membership is computed from
the committed Census code sets. The run refuses unless that result equals the comparison the
database made.

## 2. Why "0 omissions" is a measurement

An omission would be one of two failures. Each was checked against production on 2026-10-01.

**Acquisition: is `geo.zcta_boundary` missing a Census ZCTA? No.**
- `geo.zcta_boundary` holds 33,791 distinct codes, md5 (collate "C") `7e927a8e…`, all loaded from
  TIGER/Line 2025, the 2020 delineation (`tl_2025_us_zcta520.zip`, sha256 `e8712963…`). Its loader
  already asserts the 33,791 count.
- Census TIGERweb was read from Postgres through pg_net.
  - **What this check is, exactly:** independent of HomeSignal's load path, but the **same Census
    2020 data** reached by a different route. It compares **codes only, not shapes**.
- Layers read, labelled from Census's own layer metadata (requests 16686, 17177, 17179):

  | layer | Census's name | Census's group |
  |---|---|---|
  | `tigerWMS_Current/2` | 2020 Census ZIP Code Tabulation Areas ("2020 Census - January 1, 2020 vintage") | none |
  | `PUMA_TAD_TAZ_UGA_ZCTA/1` | 2020 Census ZIP Code Tabulation Areas | none |
  | `PUMA_TAD_TAZ_UGA_ZCTA/4` | 2020 Census ZIP Code Tabulation Areas | BAS 2026 |
  | `PUMA_TAD_TAZ_UGA_ZCTA/7` | 2020 Census ZIP Code Tabulation Areas | ACS 2025 |
  | `PUMA_TAD_TAZ_UGA_ZCTA/11` | ZIP Code Tabulation Areas | Census 2020 |

- **All five returned byte-identical bodies** (response md5 `f5c1c0ac…`). They are one dataset served
  five ways, so this is **one** check, not five.
- That one check holds 33,791 codes, md5 `7e927a8e…`, the same as the boundary table. So 0 codes are
  in one and not the other, in either direction.
  - Positive control: it contains all 12,016 registry ZIPs that have a boundary.
- **0 of the 706 are in it.**
- **The code sets themselves are committed** (`census-zcta-codes-2026-10-01.json`, one bitmap per
  delineation). So this can be re-checked offline after pg_net expires the responses, which happens
  about 6 hours after each read.

**Generation: does the serving generation call a boundary ZIP `not_measured`? No.**
- The ACTIVE generation at the evidence read (19:03Z) was `n5-national-2026-09-30` (activated
  18:13:50Z). The earlier version of this receipt named `n5-national-2026-09-29`, which was ACTIVE
  when first measured (about 17:20Z).
- Both mark exactly these 706 `not_measured` (md5 `7d1bf19a…`, the same as the export) and the
  other 12,016 `boundary_complete`, with 0 disagreements with the boundary table.
- `n5-national-2026-10-01` was BUILDING and had no status rows yet.
- All 12,016 registry boundaries are valid, non-empty `MULTIPOLYGON`s (SRID 4269).
- Fix 3's check (D11, applied 2026-09-29) refuses READY or ACTIVATE on any status that disagrees with
  the boundary.

**Context only: the 2010 delineation.** TIGERweb's 2010 ZCTA layer (33,144 codes; positive control
11,757) contains **9** of the 706: they had a ZCTA in 2010 and none in 2020.
- PO Box: 01086, 01467, 02651, 02669, 80511
- unique: 01199
- standard: 11351
- decommissioned: 98205, 98929

A superseded 2010 polygon is not a boundary for a current page, and none was used.

**When this could change.** None of the 706 has a ZCTA in the current (2020) delineation, which
TIGERweb still serves for its BAS 2026 and ACS 2025 groups. The next chance for any of them is the
2030 delineation. That ZCTAs are redrawn only with each decennial census was not confirmed from a
Census page, because census.gov is unreachable from the build sandbox.

**The two ZIPs whose existence is not established.** 84684 ("West Mountain"; its page name carries
no ZIP) and 84685 ("Woodland Hills") are absent from:
- zipcodes 3.0.0. It keeps 1,040 decommissioned ZIPs, so absence is not explained by retirement. It
  lists "Woodland Hills" as an acceptable city name for 84653 (Salem).
- pyzipcode 3.0.1's bundled database. That is a 2004 snapshot built from Census 1999/2000 data, so it
  is neither current nor independent of Census, and it adds little.
- both Census delineations.

So **whether either is a real ZIP is not established**. It is not shown to be a registry mistake.
Both stay `not_measured`. Whether they should be pages at all is the founder's Gold Master
question (the page-eligibility item in QUEUE). The registry was not touched.

**The classifier** (`scripts/fix4_classify_no_boundary_zips.py`) is the only place a class is
decided. It refuses to run unless:
- the export matches the database's fingerprints;
- every Census read was complete and has a non-zero positive control;
- the 2020 layers agree;
- each committed code set decodes to the count and md5 recorded for its delineation;
- Census membership computed from those sets equals the database's recorded hits;
- zipcodes is version 3.0.0, its data fingerprints to the pinned 42,789 rows, and the imported module
  is the installed one.

An unknown command-line flag is an error, not a silent write.

## 5. Retraction: the "open item" about Fix 3 was false

The `46b1f6e` version of this receipt, QUEUE.md, CLAUDE.md, the PR body and the commit message
recorded a finding: that Fix 3's check trusts `geo.zcta_boundary` to be complete, so a deleted or
short boundary table would publish a ZIP as `not_measured` and pass. **That is false.**
- The daily build does not take boundaries from `geo.zcta_boundary`. `scripts/n5_publish.py`
  (`load_boundaries`) reads the TIGER archive itself into `geo.n5_gen_zcta`, through
  `scripts/n5_shard.py::tiger_index`, which refuses unless the archive's sha256 is the pin and it
  holds 33,791 areas.
- Fix 3's D11 then compares each ZIP's status with `geo.zcta_boundary`. A deleted row makes the two
  disagree (a ZIP published `boundary_complete` with no row in the table), so READY and ACTIVATE are
  refused. That is exactly the case the existing test B2 covers. Fix 3's receipt (§5.1) describes the
  two carriers.
- A short reload through the loader is refused even earlier, by its own 33,791 count assert.

**The real residual risks:**
- A loss common to both carriers. Unlikely, because both come from one pinned file.
- A deletion after activation. That fails safe: request-time readers lose the shape for that ZIP,
  and the next build is refused.

No new guard is needed, and the proposed one is withdrawn.
