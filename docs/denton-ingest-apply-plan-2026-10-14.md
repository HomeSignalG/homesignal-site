## 2. What the consumer test proves (task 2, `test/recovery-notification-safety.test.mjs`)

- The consumers (`national-report.ts`, `changes-since-report.ts`, `property-watch.ts`, `watch-email.ts`) contain **no recovery logic of their own**. Anything the view returns with `material = true` for a change-ready project becomes "New official record". Protection lives entirely in (a) the writer's flags and (b) the view's WHERE clause. That is why the order of the apply matters.
- Negative control (2a-2c): with today's writer and today's view, a 2024-filed record first reached "now" IS emailed as "New official record" (and the email prints `Filed 2024-03-01` next to it). The hazard is real in the current production configuration.
- With the shipped #1829 writer flags and view (both parsed from the committed SQL): the recovered event is `first_detected, material=false, is_baseline=true`; the view removes it; Property Watch, Follow/Changes Since Report and the report's detected-change rule all show nothing. Two further walls were shown independently: `material=false` alone stops it even through today's view, and `not e.is_baseline` stops a recovered row that wrongly carried `material=true`.
- A genuine arrival (`material=true, is_baseline=false`) still produces the change and the "New official record" line; recovered + genuine in one window announces only the genuine one; a recovered record that later really changes status is announced as a status change.
- Limits (not proven by this test): the genuine/recovered/held CLASSIFICATION (a SQL CASE over continuity rows) is taken as an input; it is proven by `test/dev_change_recovery_pg` (reported by the caller as 114 checks / 40 mutations, not rerun here). Nothing here executes against production data or the Deno runtime (Node type-stripping imports the real TypeScript).

## 4. Customer-notification protections that must exist BEFORE any recovery backfill / scope enablement

Required (all three, in this order, each verified by its live query above): (1) #1840 applied, (2) #1829 applied with rule_version 5 live and the view carrying `NOT e.is_baseline`, (3) the Denton ZIPs' sources observed by at least one complete expanded read so that the first read is classed as baseline. Only then enable scope for the canary ZIP.

Is pausing Property Watch needed? Based on the task-2 evidence:
- **Applying the three SQL files does not require pausing it.** Each is one transaction; the consumers only see the view; before #1829 the behavior is today's, after it the recovered class is suppressed. Pausing buys nothing for the apply itself.
- **Enabling scope BEFORE #1829 is applied would leak** (test 2a-2c). That is the only dangerous ordering, and it is prevented by sequencing, not by a pause.
- A pause is a cheap belt-and-braces ONLY for the scope-enable moment (cron `property-watch-run` is `3,13,...,53 * * * *`; `follow-development-report` and report assembly are request-driven and cannot be paused by cron). It is reversible (`cron.alter_job(active := false/true)`) but it is a production write and delays legitimate watch emails by the pause length; if used, pause just before the canary ZIP's first scoped refresh and resume after the next ledger tick plus one verification query. Recommendation: not required if the sequence in section 3 is honored and verified; the founder may still choose it for the first canary only.
- Residual risks the safeguards do NOT remove (stated in the recovery file and re-confirmed): records that arrive across a coverage gap are baselined silently (a genuine filing in a gap is not announced); a customer may see an old record on a fresh report (that is a report, not a notification - out of scope for this plan); events already written by the live ledger before the apply are not retro-classified (no scope is believed ON, so none should be widened-in; **UNVERIFIED**, and not separable from ordinary first_detected rows with the columns that exist).
